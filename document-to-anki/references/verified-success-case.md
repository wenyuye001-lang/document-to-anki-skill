## 已知技术对比

此前失败文件提示：

```text
500: JsonError { info: "decoding decks: JsonError" }
```

静态对比两版旧式 APKG：均可解压、均含 `collection.anki2` 和 `media`，数据库中 notes 与 cards 数量相同，笔记类型含 `Front`、`Back` 两字段，模板使用 `{{Front}}` 和 `{{Back}}`。

成功版相较失败版的可见差异：在 `col.decks` 中除目标牌组外还包含默认牌组，并补齐每日学习统计字段 `newToday`、`revToday`、`lrnToday`、`timeToday` 等。结合成功反馈，可以将“牌组 JSON/配置信息完整性”列为排查重点。

**不要据此断言某一字段是唯一原因**：这一比较不是控制变量实验，也没有用户端具体版本信息。更稳妥的通用方法是通过兼容的 Anki 导出/打包工具生成，而不是照搬修复案例的内部 JSON。

## 在成功版本中观察到的模板

```html
<!-- Front -->
<div class=frontside>{{Front}}</div>

<!-- Back -->
<div class=frontside>{{Front}}</div><hr id=answer><div class=backside>{{Back}}</div>
```

上述为功能上已在该案例使用的结构，不要求保留 class 名称或该具体 HTML 拼写；只需保证字段名称匹配，内容能正确显示，且颜色/样式不会遮挡。

## 本次故障链和经验

1. 初版 CSV：`#columns:ID,Front,Back,Tags` 被当作卡片内容，说明文件头和字段对应不可靠。
2. 修复 CSV：正面能够显示，背面为空，说明 **Back 数据存在** 不等于 **模板引用/呈现 Back**。
3. 初版 APKG：SQLite 和 ZIP 静态检查通过，但导入仍报 `decoding decks: JsonError`，说明**静态完整性 != 软件兼容性**。
4. 结构修正版 APKG：用户明确确认导入和答案翻面均成功，证明这次针对具体交付包的技术链路已闭环。

## 可以复用的原则

- 优先生成完整 APKG，不要求用户手动编辑卡片模板。
- 简化笔记类型：`Front`、`Back` 两字段，来源/分类/关键词可嵌入 HTML 与标签。
- 牌组配置数据应由标准库/官方接口生成，勿仅以 ZIP/SQLite 完整性判定可导入。
- 交付状态逐级确认：生成 → 静态检查 → 软件导入 → 正反面显示。
- 后续每一份资料仍需重新验收，不因为这次成功而默认成功。
